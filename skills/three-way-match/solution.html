三单匹配 · 核心判据

按订单行，八项判据 + 付款守恒

判据规则结果
完整性有发票无入库 → 缺入库单；有入库无发票 → 待开票（正常）异常
供应商一致入库单、发票的供应商 = 订单供应商异常
数量收货 vs 订单；开票 ≤ 收货；开票 ≤ 订单异常
单价 · 金额发票单价 = 订单单价；发票金额 = 数量 × 单价差异 / 异常
时间发票日期不早于首次收货待核实
发票唯一性号码去空格、全半角、前导零后唯一；供应商 + 金额 + 日期唯一异常
范围完备入库单、发票引用的订单行必须存在异常
数据质量引用该订单行的入库单或发票数值无法解析、被剔除待核实
付款守恒：发票总额 = 可付金额 + 暂缓金额；可付 = min(开票, 收货, 订单) × 订单单价。每一分暂缓都能对到具体订单行。

三单匹配 · 判据边界

三单全部对上，也不等于采购一定没问题

盲区为什么抓不到处置可闭合性
分批被误判重复只比对数量单价，分批开票会被当成重复发票号归一化 + 组合指纹，已在脚本中实现🟢 已闭合
多付未收货的钱只比对开票与订单会多付开票 ≤ 收货的付款口径，已在脚本中实现🟢 已闭合
订单价格本身偏高三单一致只说明按订单执行对接框架协议价、历史价或市场价🟡 需外部锚点
入库单造假收货数量由仓库录入，可能与实物不符对接存货盘点（#20）与门禁/过磅记录🟡 需外部锚点
发票真伪号码唯一不代表发票真实对接税务发票查验平台🟡 需外部锚点
三单匹配证明的是“三张单彼此一致”，不证明“价格合理、货真到了、票是真的”——这些边界已写入 Skill 的判据覆盖声明。
三单匹配 · 过程可回溯

每个结论都能倒查回原始数据

① 逐行留痕

158 个订单行各记订单、收货、开票数量，可付、暂缓金额与问题标签。

② 输入指纹

订单、入库单、发票、供应商四个输入各记 SHA-256 指纹与行数。

③ 守恒 + 复算

发票 = 可付 + 暂缓；单据全部归集；本机独立复算与云端一致。

证据 JSON 同时输出为网页、PDF、Markdown、Excel 四种报告，付款审批可从任意一行暂缓追溯到具体入库单和发票。
